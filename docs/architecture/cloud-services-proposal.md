# Cloud recovery and account architecture proposal

CHG-026 / CHG-073 / CHG-074 · revision 1.2 · 2026-11-12 · **Proposed, not implemented or provider-selected.** Lithuania-based business, initial European market. [Current local persistence](../requirements/persistence.md) remains unchanged: IndexedDB schema 4, backup format 4, no accounts or uploaded raw audio.

## Recommendation and alternatives

Retain offline-first local practice. The owner's new Google-first account scope makes **Firebase Authentication with Google provider, Firestore metadata and private Cloud Storage snapshots** the easiest integrated prototype to evaluate. Firebase prefers redirect sign-in on mobile, but its docs warn third-party storage restrictions can break redirect when the app is on a different host. Since this app is on Cloudflare, a transparent same-origin auth-helper proxy (or another documented workaround) is required for Safari testing; a 302 is not enough. Verify on iPhone Safari and Home Screen PWA before committing to Firebase. Start with versioned backup and explicit restore, then add conflict-aware synchronization separately. Cloud preferences alone cannot restore learned sounds, gun profiles, presets and sessions after browser storage is cleared. See the [CHG-074 feature implementation needs](../business/initial-monetization-scope.md).

Firebase is a candidate, not a final provider selection. Its Storage product requires a Blaze pay-as-you-go billing plan, and Firestore's selected location cannot be changed after creation. The region, billing alerts, storage retention, account deletion and data-processing terms must be decided before creating production resources. Google sign-in does not imply Google Drive access. Do not request Drive scopes.

| Option | Components | Advantage | Cost/risk to evaluate |
| --- | --- | --- | --- |
| Cloudflare extension — working recommendation | Worker API; D1 account mapping/preferences/backup metadata/billing entitlements; private R2 snapshots; a separate managed consumer identity provider | Reuses hosting; separates small structured metadata from versioned backup objects. Current D1/R2 rates and Workers plan terms are published | Consumer authentication is extra; exact regions, support, quotas, observability and maintenance remain; a paid Workers plan starts at US$5/month if selected |
| Supabase | Managed Auth, Postgres with row-level security and private Storage; Cloudflare frontend/API where needed | Integrated consumer identity/database/storage | Official pricing currently starts at US$25/month for Pro; compare included quotas, backup/PITR, region, egress, data export and operational fit |
| Firebase — current first prototype candidate | Firebase Auth with Google provider, Firestore metadata, private Cloud Storage snapshots | One integrated Google identity/database/object-storage stack; Firebase Auth supports Google sign-in and account linking | Cloud Storage requires Blaze billing; select Firestore location before creation (it cannot be changed); evaluate region alignment, per-product costs, rules, export and vendor coupling |

Do not maintain multiple authoritative user/library databases without a reason. Cloudflare Access may protect staff administration, but is not the public consumer account system. For a Google-first account, evaluate Firebase before custom Google OAuth plus Cloudflare Worker/D1/R2; the latter reuses hosting but requires extra token validation, account/session mapping and security work. Supabase is another integrated option. Provider selection remains open; do not build a password system or store passwords locally merely to avoid a vendor fee.

Free tiers are shared account allowances, not per-customer guarantees or a continuity commitment. ## Data and recovery contract

The requested first cloud feature is backup/restore, not continuous live synchronization. A new-device restore should make the library available under the same account after the owner confirms which version to use. If both devices later edit independently, sync needs a separate revision/conflict design. The account-backed library must represent up to five gun profiles and all their owned settings, derived sound-training features, presets and durable history.

| Data | Proposed handling |
| --- | --- |
| Appearance/vibration and audio preferences | Back up values, but re-evaluate capabilities on each browser; a saved setting cannot add Safari vibration support |
| Gun names/types, derived calibration/features, custom presets and configuration | Include compatible, versioned user-owned data after explicit cloud enablement; no firearm serial number needed |
| Session/history records | Include owned results for restoration; immutable IDs/snapshots support a later merge protocol |
| Raw audio/video, payment card data and identity-provider credentials | Exclude from practice backups; no raw-audio/video upload authorized; card data stays with checkout provider |
| Paid ownership | Authoritative backend entitlement; never inferred from a backup field, local plan flag or email address |

All buckets are private. Use verified immutable identity IDs (Firebase UID in the candidate implementation), not caller-supplied email/userId, to resolve ownership. Authenticate every API request; verify token issuer/audience/signature/expiry and server-side account mapping. Apply per-account object keys/row access, quotas, bounded body/decompression/depth, rate limits and schema validation. CORS is not authorization. Use secure HttpOnly/SameSite cookies and CSRF protection if the chosen session design uses cookies; otherwise document token lifetime/storage/XSS trade-offs. Keep server keys and payment/webhook secrets out of the client.

A snapshot upload is marked complete only after object upload, checksum validation and metadata commit. Persist version, timestamp, schema, library revision and acknowledged completion; retain the previous successful snapshot on failure. Retry idempotently and reconcile orphan objects. Debounce/queue changes and upload outside active audio work. Show **Saved on this device**, **Cloud backup pending** or a real **Last backed up** time rather than claiming success before acknowledgment.

Restoration requires sign-in and a real downloadable snapshot after local storage deletion. Validate the whole payload, show source/date/contents and ask whether to replace or keep current local data; atomically restore without silently overwriting a newer local library. Keep compatible manual export/import available. Re-calibration may be needed on a different microphone even when feature vectors restore correctly.

Do not automatically attach an anonymous library to an account or upload account A's data after switching to B. Define a library/account namespace migration that preserves anonymous data and requires explicit linking. Logout cancels uploads and clears tokens/private response caches; handling local private data needs a visible retain/remove choice. A second account must not inherit another account's Pro entitlement, queued uploads, cloud rows or selected backup.

For later sync, use stable IDs, revision preconditions and conflict copies; test concurrent edits, offline queues, deletion/reset tombstones and changed preset snapshots. No silent last-write-wins replacement of an active library. Upload scheduling is foreground/PWA capability based; Safari background execution is not guaranteed.

## Proposed quotas, retention and lifecycle

Measure real backup size and change frequency first. A candidate budget is the current 10 MB uncompressed restore envelope, seven versioned snapshots and 30 days of backup retention; these are **unapproved cloud-policy hypotheses**, not new app limits. Resolve the existing large-library export/import mismatch before imposing a cloud envelope or claiming complete recovery. Define retention after cancellation separately, communicate recovery/export grace and issue deletion notice before expiry. Never delete local profiles/results on payment lapse.

Account deletion stops subscriptions/queued uploads, revokes sessions, removes user-owned cloud rows/objects and explains provider/operator backup expiry. Statutorily required billing records use separate disclosed minimum retention; they do not justify retaining practice data indefinitely. Operators need tested service backup/restore, deletion propagation, incident response and key rotation. Cloud copies do not protect against untested operator-wide corruption or mistaken deletion.

Choose a supported European data-location strategy where available and verify actual residency/transfer contracts; jurisdiction alone does not guarantee EU-only processing. Obtain DPAs/subprocessor information and define controller/processor responsibilities and access logging. No end-to-end encryption promise is made: select controlled provider/application encryption and test key recovery before marketing it.

## Separate environments and required tests

Use separate staging/production databases, buckets, auth clients, callback URLs and billing/webhook secrets. Never copy real firearm/profile data into fixtures. Public staging is noindex and staff-only where appropriate; fake paid grants cannot enter production builds.

Acceptance: Authenticated user A cannot enumerate/read/write B in both Firestore and Storage Rules Emulator tests; revoked/expired tokens are denied; Google redirect sign-in, anonymous-account linking/collision and account switching are tested on target browsers; duplicate/reordered uploads are safe; a failed snapshot preserves the last good one; browser-data deletion followed by sign-in restores the correct complete library; account switching/concurrency never mixes owners; cancelled Pro preserves local records and disclosed restore access; deletion propagates. These tests are unrun until services exist. See [billing/QA requirements](../business/monetization.md).
