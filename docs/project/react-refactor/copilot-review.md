# Review of the two Copilot architecture analyses

Reviewed 2026-10-24 against local `b` revision `2cf044c`, application revision `5b8aeed`. The supplied analyses do not identify their source branch or commit; their observations cannot be assumed to describe the latest `b`. This is a review and proposed follow-up, not approval or implementation of another migration. Main/dev remain unchanged.

## Verdict

Accept the maintainability diagnosis for `main.js` and `storage.js`, and the recommendation to preserve domain contracts. Do not execute the proposed migration phases as written: they repeat completed screen migration, introduce overlapping ownership locations, and conflict with the measured progressive-startup decision. File organization alone is not evidence of a performance or security defect, and moving files does not establish a speed improvement.

The approved React refactor is complete within [ADR001](../../architecture/decisions/001-progressive-react-startup.md). Further modularization can improve maintenance without restarting that migration or replacing its architecture.

## High-risk invariants missing from the proposed map

1. **Atomic persistence:** `deleteGun` deletes all owned records and changes selection in one transaction; `restoreBackup` validates the whole input before one replacement transaction; `exportBackup` reads a consistent multi-store snapshot. Splitting these into independently committed feature operations would change behavior and could leave partial data.
2. **Startup I/O:** `getLibraryOverview` batches guns, selected ID and device preferences into one read-only snapshot. Replacing it with several feature/provider loads would undo a measured optimization and can produce inconsistent startup state.
3. **Capture ownership:** keep operation/capture tokens, serialized queues, cancellation and save-failure guards. React mount/unmount or StrictMode must not duplicate microphone acquisition, cues, timers or durable writes.
4. **Exclusive rendering:** preserve native-to-React handoff, rollback, exact uncontrolled input/file nodes, invalid drafts, focus and delayed/failed chunk behavior. “No DOM manipulation in controllers” is a possible long-term presentation goal, not permission to remove working startup paths now.
5. **Edition/security boundary:** public creation limits and retained saved-data access must remain; private preview authentication, private assets, no-store/offline policy and Free/Full simulation cannot become a public client-side switch.
6. **Acceptance:** unchanged visuals, guide frames/GIF content, data schemas/formats, audio/timing behavior, original minified payload/timing budgets and both-edition browser tests. A path refactor should not require visual or performance rebaselining.

## Recommended follow-up order — proposed only

1. **Document seams and strengthen boundary checks.** Inventory the dependencies/closure state to be extracted and permitted import directions. Correct documentation drift: the architecture handoff still says 38 packages, while the checker verifies 39 (13 pages + 26 UI); a Practice controller comment still says six modes although four remain. Keep the completed P0–P8 plan intact and track any approved follow-up separately.
2. **Extract pure persistence validation.** Move backup/session normalization and validation into internal modules with direct behavior tests and the same public `storage.js` facade. No schema bump, new data copy, transaction restructuring or new provider/store is needed for this slice.
3. **Extract cohesive orchestration from main, one responsibility at a time.** Start with preferences or gun-library coordination, based on an explicit closure/dependency map. Keep main as composition root; avoid a generic bucket of all view functions or all event handlers. Preserve startup snapshot batching and profile/capture/save locks.
4. **Consolidate controller presentation where useful.** Extend existing models/ports while keeping engines and service lifecycles independent of React. Native startup and mounted React must consume the same decisions without two simultaneous writers.
5. **Organize remaining domain files/CSS only where the previous slices reveal a real benefit.** Introduce public module entries and targeted selector scoping without a blanket rename, new routing library, provider hierarchy or duplicate shared folder.

Each implementation slice needs characterization before extraction, unit/coverage and integration checks, public/preview minified builds, pinned Chromium/WebKit screenshot/workflow suites and unchanged original performance gates before b publication. Main/dev remain frozen unless the owner changes that instruction. These steps are recommendations, not started implementation.

Owner asked why main/apps/web/src/pages contains only About/Contact and whether DrillSetupPage/DrillRunPage/DrillAboutPage should be shared. Remote refs verified: main6c38bff has only AboutPage/ContactPage in that folder; b2cf044c has all13 page packages. Main remains intentionally unpromoted; no merge is authorized by this question.

Proposed names DrillSetupLayout, DrillRunLayout and DrillGuideLayout distinguish shared presentation from screens/routes and independent timing/capture controllers. AppShell continues to own global header/footer/navigation. Setup/run/review remain states of existing screens; extracting templates does not require new routes or a single merged engine. Consolidate duplicated content where demonstrated; renaming folders alone is not reuse. This is architectural advice only, not authorization to implement or promote main/dev.

## B-only assessment: Live Listen, Settings and History

All three already have a dedicated page package (source/CSS/component tests/export), share AppShell and PageHeading and use separate mount/presentation/service ownership. Their content serves different workflows; they should remain separate pages composed from focused components.

- LiveListenPage still contains substantial inline content: mode/sequence panel, listening controls/readiness/sensitivity, microphone level, bounded session timeline and latest recognition/verification. Extract cohesive feature sections when this improves testing/readability; that alone does not make them globally shared. A microphone-level presentation is a plausible shared component with Practice, provided different presentation variants and the existing high-frequency update port remain intact. Transient live timelines and persistent verified History records should not be treated as identical data/components.
- SettingsPage repeats group headings/descriptions, preference-toggle rows and action rows. A SettingsSection/PreferenceToggle/SettingsAction family would reuse concrete repeated markup. Retain browser-support explanations, gun/device preference scope, the actual native file input and independent private preview subtree; destructive actions keep confirmation/service ownership outside presentation.
- HistoryPage already composes SavedSessionList, RecognitionList and EvaluationPanel, with separate retained numeric-limit and optional progress content. Further extraction is lower priority; a real duplicated section/status/context primitive may help, but another History wrapper adds little. Preserve draft verification selections, gun ownership, separate history/session deletion and private progress guards.

Across these pages and Practice/Sequence, the gun-context paragraph is a concrete repeated candidate for a shared GunContext component. Extend the existing shared UI home and page-heading/shell contracts; do not add separate per-page headers/footers/navigation or force unlike content into one generic page. Suggested priority for these three pages: Settings repeated rows, then Live Listen feature sections/shared meter, then small History cleanup only if an actual duplicate remains. Review only; no implementation has been authorized by the questions.
